# 为 pi 贡献

本指南的存在是为了节省双方的时间。

## 理念

首先要说的是：**pi 的核心是最小化的**。

如果你的功能不属于核心，它就应该是一个 extension。让核心膨胀的 PR 很可能会被拒绝。

Pi 的核心存在的意义是最小化且可扩展，以便它能够被 extension 影响和操纵。 然而即便是面向 extension 的 hook 点也应该经过充分考虑和讨论，以避免添加不可维护的膨胀和复杂的交互。

## 唯一规则

**你必须理解你的代码。** 如果你无法解释你的变更做了什么，以及它们如何与系统其余部分交互，你的 PR 就会被关闭。

使用 AI 写代码是可以的。提交你不理解的 AI 生成的 slop 则不行。

如果你使用 agent，请从 `pi` 根目录运行它，这样它会自动读取 `AGENTS.md`。你的 agent 必须遵循该文件中的规则和指南。

## 贡献准入门槛

来自新贡献者的所有 issue 和 PR 默认都会被自动关闭。

周五到周日提交的 issue 不保证会被审查。 如果有紧急事项，请在 Discord 上询问：https://discord.com/invite/3cU7Bz4UPx

维护者每天审查被自动关闭的 issue，并重新打开有价值的那些。不符合下方质量标准的 issue 不会被重新打开，也不会收到回复。

批准通过维护者在 issue 上的回复来实现：

- `lgtmi`：你未来的 issue 不会被自动关闭
- `lgtm`：你未来的 issue 和 PR 不会被自动关闭

该命令必须位于回复的开头（可选地在一个或多个 `@username` 提及之后）或结尾。`lgtmi` 不授予提交 PR 的权利。只有 `lgtm` 授予提交 PR 的权利。

## Issue 的质量标准

如果你开一个 issue，你必须使用两个 GitHub issue 模板之一。

如果你开一个 issue，请保持它简短、具体、值得一读。

- 保持简洁。如果它无法在一屏内放下，那就太长了。
- 用你自己的声音来写（不要用 LLM 生成文字，如果一定要用，请随后附上一条明确标注为 AI 的评论）。
- 清楚地陈述 bug 或请求。
- 解释它为什么重要。
- 如果你想自己实现该变更，请说明。

如果该 issue 是真实的且写得好，维护者可能会重新打开它，或在上文所述的命令位置回复 `lgtmi` 或 `lgtm`。

## 拉黑

如果你两次无视本文档，或者你用 agent 生成的 issue 刷爆 tracker，你的 GitHub 账号将被永久拉黑。

如果你通过自动化发送大量 issue，你的 GitHub 账号将被永久拉黑。概不反悔。

## 提交 PR 之前

除非你已经通过维护者在上文所述命令位置使用 `lgtm` 获得批准，否则不要开 PR。

在提交 PR 之前：

```bash
npm run check
./test.sh
```

两者都必须通过。

不要编辑 `CHANGELOG.md`。变更日志条目由维护者添加。

如果你要向 `packages/ai` 添加一个新 provider，请参见 `AGENTS.md` 了解必需的测试。

## FAQ

### 为什么新 issue 和 PR 会被自动关闭？

pi 收到的 issue 数量超过维护者能够实时负责任地审查的数量。许多报告不符合本指南中的质量标准，或者不遵循 CONTRIBUTING.md。有些是通过 agent 漫不经心地甩到仓库里的，而不是由提交它们的人审查和打磨过的。自动关闭创建了一个缓冲，让维护者可以按自己的节奏审查 tracker，并重新打开那些符合质量标准的 issue。

### 为什么周末的 issue 优先级更低？

我们在工作时间内对 tracker 进行分诊。这意味着周末可能会积累更多 issue。周五到周日提交的任何内容都可能在周一审查队列中被遗漏或给予较低的优先级。如果某个问题很紧急，请在 Discord 上询问，并附上简短版本、repro 和相关日志。

### 为什么有些 issue 得不到回复？

回复也是一项维护工作。低信号 issue、不清楚的报告、重复项，以及不遵循本指南的 issue 可能会被不经讨论地关闭。这能把时间留给可复现的 bug、经过深思熟虑的请求，以及那些已经做了工作使自己报告可操作的贡献者。

### 为什么不干脆让 AI 分诊一切？

AI 可以帮助对重复项分组、总结报告，以及发现缺失的信息。但它不被信任来做出维护者的最终决定。打磨过的 AI 生成 issue 仍可能是错误的、误导性的，或调查成本高昂的。人工审查仍然是最后一道关卡。

### 这对贡献者有敌意吗？

没有。这是一道防止倦怠和 tracker 垃圾的护栏。简短、具体、可复现的 issue 是受欢迎的。经过深思熟虑的贡献是受欢迎的。自动化的 slop、理所当然的态度，以及大量低投入的报告则不受欢迎。
