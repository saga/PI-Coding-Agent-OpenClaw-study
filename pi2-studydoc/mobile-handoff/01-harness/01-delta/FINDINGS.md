# 01-delta：已知缺陷与实测发现

这里的一切都是在 `delta.md` 及其旁边的原型实现写就**之后**才发现的。其中没有任何一项被应用到本目录中的代码。生产代码现在位于 `packages/chord/src/delta/index.ts`：flush 时脏跟踪解决了 D1，生产环境重新测量在不新增 API 的情况下关闭了 D2。见 [`append-decision.md`](append-decision.md)。下面每一项仍然是原始的问题、证据和候选修复记录。

每个数字都是用 **`node --experimental-strip-types`** 测量的，而不是 `tsx`。
这很重要：tsx 通过 esbuild 转译，把同一个基准测试夸大了
**2.6 倍**（每次写入 183 µs vs 63 µs）。不要通过
transpiler 对这个模块做基准测试。

---

## D1. 交错路径击败合并（贴近正确性，内存无界）

**严重程度：高。** 这是首先要修复的那个。

### 问题

`flush()` 只合并**相邻**的 op。因此，在两个
路径之间交替的生产者永远不会合并任何东西，ops 数组随
写入次数增长，而不是随值的大小增长。

这不是假设。这正是 bash 所做的：它在每个 chunk 上更新输出文本
和一个字节计数器。

```ts
const next = t.state.content[0].text + chunk;
t.state.content[0].text = next.length > CAP ? next.slice(next.length - CAP) : next;
t.state.truncation.totalBytes += chunk.length;    // <- the other path
```

### 证据

50 KB 窗口，200 字节的 chunk，中间不 flush：

| 被扣住的写入 | ops | bytes |
| --- | --- | --- |
| 1 | 3 | 0.3 KB |
| 100 | 201 | 26 KB |
| **1000** | **2001** | **264 KB** |

没有交错时，同样的工作负载给出 1 个 op 和 51 KB。窗口
被限制在 50 KB；描述它的 ops 则不是。

### 为什么它的意义不止于内存

任何 sink **扣住** 内容的设计 — rate limiting、backpressure、缓慢的
消费者 — 都依赖于被扣住的写入不产生成本。它们当前的成本是
一切。见 `../../04-tool-output/rate-limiting.md`。

### 候选修复

在**记录**时折叠，按路径而不是按相邻性作为键：每个
路径一个槽，最多持有两个 op（`[s]`、`[d]`、`[t]`、`[a]` 或 `[t, a]`），按
首次触碰顺序发出。

一个原型在同样的工作负载上达到了 **2 ops / 51 KB**。它没有包含在
这里，因为它没有按照本单元其余部分所达到的标准得到验证。

**四条折叠规则，每一条都是关于该词汇表的一个具体主张：**

1. 同一路径上较晚的 `s` 取代较早的 `s` — 但**不**取代较早的
   `d`，后者必须存活，否则该 key 在重新插入时会改变位置（§5.1）。
2. 连续的 `a` 合并。一旦合并后的 append **严格长于**
   值，就说明窗口一直在滑动，append 是更昂贵的
   拼法，因此折叠为 `s`。严格地说：当字符串仍在朝其上限*增长*时，
   append 等于该值，在那里折叠会导致每个批次都重发
   整个字符串。
3. 一条路径上的 `t` 和 `a` **可交换** — truncate 从前面丢弃，
   append 添加到末尾 — 所以滚动窗口的 `t,a,t,a,...` 折叠为各一个。
   没有这一点，成对合并根本不会触发。
4. 在待处理的 `s` 之后的 `t` 或 `a` 不改变任何东西：`s` 已经意味着“这条
   路径变为它当前的值”。

**那个原型踩到的陷阱。** 槽按首次触碰顺序发出，这丢失了
一个子写入发生在较晚的父写入*之前*这一事实：

```
script  : a={x:1}; a.b=99; a={c:2}
producer: {"a":{"c":2}}
replica : {"a":{"c":2,"b":99}}      <- WRONG
```

在记录时，set 或 delete 必须使其路径**之下**的每一个待处理槽失效。
现有的 `verify-dead` 风格测试在这个问题存在时通过了 1190 个序列，
因为它的生成器只嵌套了一层。任何针对此的测试都必须
生成真正嵌套的路径，并在子写入之间交错父覆写。

## D2. `overlap()` 占原型 tracker 时间的 94.5% — 已关闭

**历史严重程度：高。生产决策：** 不添加显式的 append/truncate API。原型 profile 被一条缓慢的 `startsWith` 路径主导；生产代码使用扁平切片比较，本地测得每次 200 KB assistant append flush 为 17.8–18.7 µs，每次 50 KB 滚动窗口 flush 为 2.43–2.46 µs。见 [`append-decision.md`](append-decision.md)。原始证据如下。

### 问题

tracker 通过搜索两个 50 KB 字符串来推断“你 append 并逐出了”。
由 `next.slice(-CAP)` 产生的每个新值都是一个 V8 `SlicedString` — 一个惰性
子串 — 而 `indexOf`/`endsWith` 迫使它**扁平化**，每次
调用复制 50 KB。

### 证据

一个 20 000 次写入的滚动窗口循环的 CPU profile，node，在末尾 flush：

```
  94.5%  overlap
   2.7%  (anon)
   1.2%  (garbage collector)
   0.5%  set
   0.3%  emit
   0.0%  fold
```

而扁平化是可以直接观察到的：

| 50 KB 窗口上的 `overlap()` | µs |
| --- | --- |
| 复用的同两个字符串 | 37 |
| **每次调用都新建的切片字符串** | **149** |

一个较早的基准测试报告了 29 µs，因为它把两个已经扁平化的
字符串复用了 2000 次 — 一个在真实循环中永远不会出现的情况。**不要针对
复用的 fixture 对字符串操作做基准测试。**

### 候选修复

不要推断生产者已经知道的东西。`ToolOutput` 执行窗口化，
因此它可以直接发出 ops，而不是赋值一个新字符串然后让
tracker 去搜索差异：

```ts
out.append(chunk);       // -> ["t", path, dropped], ["a", path, chunk]
```

两个整数 — append 的字符数、逐出的字符数 — 描述了在有界窗口的任意两次
观察之间发生的一切。这种形态的一个原型在
各种负载下都在内存中**恰好持有那个窗口**，没有 ops 数组，没有 overlap
检测，也完全没有折叠规则。

这**并不**移除 `overlap`：它在生产者赋值一个全新字符串、
delta 确实必须被发现的通用情况下保留。它把
它从热路径中移除。

### 不要

在做上述事情之前，不要“优化” `overlap` 本身。它的算法
已经正确且有界（`maxOverlapScan`）；成本是字符串扁平化，
没有任何探测策略能避免。

## D3. 嵌套路径 proxy 开销是下一个，且目前不可见

**严重程度：未知 — 行动之前先测量。**

`overlap` 如此彻底地主导，以至于 profile 中看不到其他东西。但两个
基准测试的分歧指向了路径深度：

| | 每次写入的 µs |
| --- | --- |
| 顶层路径（`{ text }`） | 63 |
| 嵌套路径（`{ content: [{ text }] }`） | 244 |

仅深度一项就是 4 倍。每次嵌套属性访问都会包裹一个子 proxy 并通过拼接
路径构建缓存 key，因此读取 `content[0].text` 在每次
访问时都会分配。

**只有当生产环境 delta 成本变得重要时才重新 profile。** 这可能是下一个瓶颈，也可能
什么都不是；当前的数字无法区分它们，因为 `overlap` 淹没了二者。

## D4. 经过测量并发现不值得我们做的事情

记录下来，免得有人重复这些工作。在上面那个
profile 中，它们合计都在 **1.5%** 以下。

**用 path trie 取代 `JSON.stringify(path)` key。** 在
孤立情况下确实更快 — 在 `LaneSnapshot` 形态上快 6 倍，在 500 条不同路径上快 93 倍 — 因为
stringify 成本随路径深度增长，而 trie 遍历是每段一次 `Map.get`。但整个 slot 层只占运行时的 0.5%。只有当当前的生产 profile 这么说时才构建它。

**trie 作为存储 vs trie 作为索引。** 如果真的要构建 trie，它应该把路径映射到
**ops 数组中的位置**，而不是持有 ops。持有它们会丢失首次触碰
顺序，并迫使在 flush 时排序来重建它。测得的差异：没有
（1.4x / 0.9x / 1.0x）。这个论点是结构性的，不是性能性的。

**用 `maxDepth` 启发式跳过后代扫描。** 被拒绝：flat map 在
常见情况下也处于劣势，所以该启发式会隐藏一个真实的成本，
而不是移除它。

**在 `a`+`a` 合并中进行急切字符串拼接。** 真实（它每次写入都重建一个不断增长的
字符串），但只值约 5%。比较长度，只在
发出时物化。

## D5. 产生这些数字时犯下的测量错误

列出来是因为每一个都产生过一个自信的错误结论，而这些陷阱
仍然存在。

- **通过 `tsx` 做基准测试** — 把一切都夸大了 2.6 倍。
- **在字符串基准测试中复用已扁平化的字符串** — 把真实成本隐藏了 4 倍。
- **重复性的 fixture**（`"x".repeat(n)`）— overlap 检测撞到它的候选
  上界并放弃，所以基准测试测量的是回退路径，而不是真实路径。
  使用多样化的文本。
- **把缓存命中当作工作来测量** — 当文本和宽度未变时 `Markdown.render()` 返回
  `cachedLines`，所以一个重复同一调用的循环
  把成本为 0.86 ms 的东西测成了 0.065 ms。
- **在常数项占主导时对复杂度进行推理** — 两次。
- **测量 heap 而不是 retained size** — 一个生成 800 x 1 MB
  字符串的 fixture 报告了 40 MB 的“增长”，那其实是它自己的垃圾。
