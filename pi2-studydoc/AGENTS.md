# 开发规则

## 对话风格

- 保持回答简短、简洁
- 在 commit、issue、PR 评论或代码中不使用 emoji
- 不使用废话或欢快的填充文字（例如用 "Thanks @user" 而非 "Thanks so much @user!"）
- 只写技术性文字，直接了当
- 使用简洁、清晰、简单的语言。在使用不可避免的术语之前先定义它。
- 把非平凡的设计和问题解释为：问题、具体示例或简短追踪，然后是解决方案。说明为什么该解决方案是必要的，并将其与可选复杂度区分开。
- 优先使用具体行为和小的示例，而不是抽象总结、密集术语或未经解释的变更列表。
- 当用户提出问题时，先回答问题，再进行编辑或运行实现命令。
- 在回应用户反馈或某项分析时，先明确说明你是同意还是不同意，再说你改了什么。

## 代码质量

- 在进行大范围变更之前、在编辑你尚未完整检查过的文件之前，以及在要求调查或审计时，完整阅读文件。不要依赖搜索片段来进行大范围变更。
- 除非绝对必要，否则不使用 `any`。
- 对只有一个调用点的单行 helper 进行内联。
- 到 node_modules 中检查外部 API 类型；不要猜测。
- **禁止内联 import**（`await import()`、`import("pkg").Type`、动态类型 import）。只使用顶层 import。
- 绝不要为了修复过时依赖导致的类型错误而移除或降级代码；而是升级该依赖。
- 在由根配置检查的代码（`packages/*/src`、`packages/*/test`、`packages/coding-agent/examples`）中，只使用可擦除的 TypeScript 语法（Node strip-only 模式）：不使用 parameter properties、`enum`、`namespace`/`module`、`import =`、`export =` 或其他需要 JS 输出的构造。使用显式字段加构造函数赋值。
- 在移除看似有意为之的功能或代码之前，务必先询问。
- 除非用户要求，否则不要保留向后兼容性。
- 绝不要硬编码按键检查（例如 `matchesKey(keyData, "ctrl+x")`）。把默认值加到 `DEFAULT_EDITOR_KEYBINDINGS` 或 `DEFAULT_APP_KEYBINDINGS`，以便它们保持可配置。
- 绝不要直接修改 `packages/ai/src/models.generated.ts`；而是更新 `packages/ai/scripts/generate-models.ts`，然后重新生成。包含由此产生的 `models.generated.ts` diff 总是可以的，即使重新生成包含了无关的上游 model metadata 变更。

## 命令

- 在代码变更（非文档）之后：运行 `npm run check`（完整输出，不要 tail）。在 commit 之前修复所有 error、warning 和 info。它不会运行测试。
- 除非用户要求，否则绝不要运行 `npm run build` 或 `npm test`。
- 绝不要直接运行完整的 vitest 套件：它包含在存在 endpoint/auth 环境变量时会激活的 e2e 测试。对于所有非 e2e 测试，从仓库根运行 `./test.sh`。否则从包根运行特定测试：
  - Vitest：`node "$(git rev-parse --show-toplevel)/node_modules/vitest/dist/cli.js" --run test/specific.test.ts`
  - `packages/tui`（`node:test`）：`node --test test/specific.test.ts`
- 如果你创建或修改了测试文件，运行它并迭代测试或实现，直到它通过。
- 对于 `packages/coding-agent/test/suite/`，使用 `test/suite/harness.ts` + faux provider。不使用真实的 provider API、key 或付费 token。
- 在修复某个 github issue 的回归测试中，在测试旁边添加一条带有该 github issue 编号的注释。
- 对于临时脚本，将其 `write` 到临时文件（例如 `/tmp`），运行，如有需要就编辑，完成后删除。不要把多行脚本嵌入 `bash` 命令中。
- 除非用户要求，否则绝不要 commit。

## 依赖与安装安全

- 把 npm 依赖和 lockfile 变更视为需要审查的代码。直接外部依赖保持固定到精确版本。
- 更新 `undici` 时，你**必须**阅读目标版本的 changelog/release notes，并在应用更新之前评估是否有任何变更可能影响功能。
- 使用 `npm install --ignore-scripts` 在本地 hydrate/update；使用 `npm ci --ignore-scripts` 进行 clean/CI 风格的操作。除非用户要求，否则不要运行生命周期脚本。
- 如果依赖 metadata 发生变化，使用 `npm install --package-lock-only --ignore-scripts` 刷新 `package-lock.json`。
- 如果 `packages/coding-agent/npm-shrinkwrap.json` 需要重新生成，运行 `node scripts/generate-coding-agent-shrinkwrap.mjs`（用 `--check` 或 `npm run check` 验证）。带有生命周期脚本的新依赖需要审查，并在该脚本中显式加入 allowlist 条目；绝不要悄悄添加一个。
- Pre-commit 会阻止 lockfile 提交，除非设置 `PI_ALLOW_LOCKFILE_CHANGE=1`。除非用户希望提交该 lockfile 变更，否则不要绕过。

## Git

多个 pi session 可能同时在此 cwd 中运行，每个都在修改不同的文件。触及你自己变更之外未暂存、已暂存或未跟踪文件的 Git 操作会践踏其他 session 的工作。请遵循这些规则：

提交：

- 只提交你在**本次** session 中更改的文件。
- 暂存显式路径（`git add <path1> <path2>`）；绝不使用 `git add -A` / `git add .`。
- 在提交之前，运行 `git status` 并确认你只暂存了自己的文件。
- `packages/ai/src/models.generated.ts` 总是可以和你的文件一起包含。
- Message 格式：`{feat,fix,docs}[(ai,tui,agent,coding-agent)]: <commit message> (optionally multiple lines)`。Message 应信息丰富且简洁。

绝不要运行（会破坏其他 agent 的工作或绕过检查）：

- `git reset --hard`、`git checkout .`、`git clean -fd`、`git stash`、`git add -A`、`git add .`、`git commit --no-verify`。

如果发生 rebase 冲突：

- 只在你修改过的文件中解决冲突。
- 如果冲突出现在你没有修改过的文件中，则中止并询问用户。
- 绝不要 force push。

## Issue 与 PR

关于贡献者准入门槛（自动关闭 workflow、`lgtm`/`lgtmi`、质量标准），参见 `CONTRIBUTING.md`。

在审查 PR 时：

- 除非用户明确要求，否则不要运行 `gh pr checkout`、`git switch`，或以其他方式把工作区移动到该 PR 分支。
- 使用 `gh pr view`、`gh pr diff`、`gh api`，以及针对已 fetch ref 的本地 `git show`/`git diff` 来检查 PR metadata、commit 和 patch，而不切换分支。
- 如果你需要 PR 文件内容，请将它们 fetch/读取到临时文件，或使用 `git show <ref>:<path>`，而不切换分支。

在创建 issue 时：

- 为受影响的包添加 `pkg:*` 标签（`pkg:agent`、`pkg:ai`、`pkg:coding-agent`、`pkg:tui`）；所有适用的都要用上。

在发布 issue/PR 评论时：

- 将评论写入临时文件，并用 `gh issue/pr comment --body-file` 发布（绝不要通过 `--body` 传多行 markdown）。
- 保持评论简洁、技术性、符合用户的语气。
- 每条由 AI 发布的评论都以发起该评论的 prompt 所指定的 AI 生成免责声明行结尾（例如 `This comment is AI-generated by `/wr``）。

在通过 commit 关闭 issue 时：

- 在 message 中包含 `fixes #<number>` 或 `closes #<number>`，以便合并时自动关闭该 issue。对于多个 issue，为每个 issue 重复该关键字（`closes #1, closes #2`）；共用一个关键字（`closes #1, #2`）只会关闭第一个。

## 变更日志

位置：`packages/*/CHANGELOG.md`（每个包一个）。

`## [Unreleased]` 下的章节：`### Breaking Changes`（需要迁移的 API 变更）、`### Added`、`### Changed`、`### Fixed`、`### Removed`。

规则：

- 所有新条目都放在 `## [Unreleased]` 下。先阅读整个章节，并追加到已有的子章节；绝不要重复它们。
- 已发布版本的章节（例如 `## [0.12.2]`）是不可变的；绝不要修改它们。
- 当在 `main` 以外的分支或 pull request 上工作时，不要创建 changelog 条目

署名：

- 内部（来自 issue）：`Fixed foo bar ([#123](https://github.com/earendil-works/pi/issues/123))`
- 外部贡献：`Added feature X ([#456](https://github.com/earendil-works/pi/pull/456) by [@username](https://github.com/username))`
