收尾。

额外指令：$ARGUMENTS

首先从对话历史中确定上下文。

上下文检测规则：
- 如果对话中已经提到某个 GitHub issue 或 PR，则使用该现有上下文。
- 如果工作来自 `/is` 或 `/pr`，则假定 issue 或 PR 上下文已从对话以及已完成的分析工作中得知。
- 如果对话历史中没有 GitHub issue 或 PR，则将其视为非 GitHub 工作。

除非我在本次请求中明确覆盖某些内容，否则按顺序执行以下操作：

1. 使用仓库的变更日志规则，在 `## [Unreleased]` 下添加或更新相关包的变更日志条目。
2. 如果此任务与某个 GitHub issue 或 PR 相关联，且本次 session 中尚未发布最终的 issue 或 PR 评论，则用我的语气起草它，预览它，并只发布恰好一条最终评论。该评论必须以这条完全一致的独立免责声明行结尾，不得有任何变体：

   ```text
   This comment is AI-generated by `/wr`
   ```
3. 只提交你在本次 session 中更改的文件。
4. 如果此任务恰好与一个 GitHub issue 相关联，在 commit message 中包含 `closes #<issue>`。如果它与多个 issue 相关联，停下来并询问使用哪一个。如果它与任何 issue 都不关联，则不要在 commit message 中包含 `closes #` 或 `fixes #`。
5. 检查当前 git 分支。如果不是 `main`，停下来并询问该怎么做。除非我明确说明，否则不要从其他分支 push。
6. push 当前分支。
7. 如果此任务恰好与一个 GitHub issue 相关联，在 push 之后以原因 `completed` 明确关闭该 issue，以便 `.github/` 中的 issue-close workflow 运行。这仅适用于 issue，不适用于 PR。
   - 检查 `gh issue view <issue> --json state,stateReason,labels`。
   - 如果该 issue 是打开的，运行 `gh issue close <issue> --reason completed`。
   - 如果该 issue 已关闭且原因为 `COMPLETED` 以外的任何值，先重新打开它，然后用 `gh issue close <issue> --reason completed` 关闭它，以便 GitHub 发出一个新的 close 事件。
   - 如果该 issue 已作为 `COMPLETED` 关闭，则保持关闭，除非 `inprogress` 标签仍然存在；在这种情况下，重新打开它并以原因 `completed` 再次关闭它。

约束：
- 绝不要暂存无关文件。
- 绝不使用 `git add .` 或 `git add -A`。
- 如果代码有变更，在提交前运行必需的检查。
- 除非我明确要求，否则不要开 PR。
- 如果这不是 GitHub issue 或 PR 工作，不要发布 GitHub 评论。
- 如果本次 session 中已经发布过最终的 issue 或 PR 评论，除非我明确要求，否则不要再发布一条。
- 当针对 `main` 以外的分支工作时，跳过变更日志。
